LUNA-REG user instructions

LUNA-REG is a lunar image-registration system designed for Chandrayaan-2 OHRC, TMC-2 and IIRS imagery. Read the workflow below before uploading a pair.

Recommended: For real Chandrayaan-2 products, use Image + XML mode so geographic overlap, sensor information, GSD and illumination metadata can be used during registration.

01

How to use the website

Follow these steps for every registration run.

1

Choose the input mode

Image + XML is recommended for real PDS4 products. Image Only is intended for testing or when metadata is unavailable.

2

Upload two observations

Select Image 1 and Image 2. Supported website inputs include PNG, JPG, TIFF, BMP and PDS4 .IMG. In metadata mode, attach the matching XML label for each .IMG.

3

Select the matching strategy

AUTO is recommended. It uses the adaptive workflow with SIFT and RIFT2 fallback. You can also force SIFT-only or RIFT2-only for experiments.

4

Set the reference in Image Only mode

When metadata is not available, choose which uploaded image should act as the reference. In metadata mode, LUNA-REG can use sensor/GSD information to help assign roles.

5

Run registration

The system analyzes scale, rotation, illumination and image conditions; generates correspondences; applies RUCO/TAT filtering, spatial balancing and robust geometric verification.

6

Read the result dashboard

Check ACCEPTED / REJECTED, inliers, inlier ratio, RMSE, reprojection error, spatial coverage, selected branch, overlays, difference image and diagnostic match images.

02

Input mode guide

Use the mode that matches your data.

RECOMMENDED

Image + Metadata

Provide Image 1 + XML and Image 2 + XML.

  • Automatic OHRC / TMC-2 / IIRS identification
  • GSD and scale information
  • Sun elevation / azimuth analysis
  • Latitude / longitude footprint information
  • Geographic overlap and common ROI extraction
  • Georeferenced output information when available
TESTING MODE

Image Only

Provide only two normal or supported image files.

  • Useful for synthetic and controlled tests
  • User selects the reference image
  • No metadata-based geographic overlap validation
  • No metadata-driven sensor/GSD/sun-angle reasoning
  • Registration depends entirely on visual correspondence
03

Current LUNA-REG pipeline

This is the workflow currently implemented in the project.

Adaptive preprocessingGrayscale / normalization, CLAHE and illumination-aware representations where needed.
Adaptive FMTProvides coarse scale and rotation diagnostics and can support scale normalization.
ARSSUses image conditions and available metadata to select an appropriate matching strategy.
RUCO / TATImproves correspondence reliability with filtering, geometric consistency and spatial balancing.
RANSAC / MAGSAC stageRejects outliers and estimates the geometric transformation from verified correspondences.
Quality validationUses inliers, inlier ratio, reprojection error / RMSE, spatial coverage and match distribution.
04

Important usage notes

Registration is only meaningful when the image pair contains sufficient common lunar terrain.

Overlap matters

Two different regions should be rejected. For real products, metadata mode checks geographic footprint overlap before the expensive registration stages.

Large files take time

Raw Chandrayaan-2 .IMG products can be very large. Runtime depends on image size, overlap, selected feature strategy and whether fallback processing is required.

Do not judge by one metric

A high inlier ratio alone is not enough. Inspect RMSE/reprojection error, spatial coverage, match distribution and visual overlays together.

RIFT2 is the heavier fallback

Use it for difficult multi-modal or illumination-different pairs when SIFT is insufficient. AUTO is usually the safest starting strategy.

05

Remaining & future work

Planned improvements beyond the current implementation.

Remaining work — short term

  1. Integrate SuperPoint + LightGlue into ARSS as an additional deep-learning matcher alongside SIFT and RIFT2.
  2. Benchmark all matchers on OHRC, TMC-2 and IIRS pairs using the same quality metrics.
  3. Improve RUCO correspondence scoring, filtering, spatial balancing and outlier rejection.
  4. Strengthen Image Only mode for difficult scale, rotation and illumination differences.
  5. Validate on more real overlapping pairs and difficult lunar edge cases.

Future work — long term

  1. Smarter ARSS condition-based strategy selection across classical and learned matchers.
  2. Faster processing through GPU acceleration, caching and code optimization.
  3. Advanced refinement with stronger sub-pixel and local-deformation handling where scientifically justified.
  4. Confidence-aware results with interpretable confidence scores and quality maps.
  5. Batch registration & mosaicing for multiple overlapping lunar observations.
  6. Web deployment & collaboration with improved remote access, reporting and robustness.
  7. Generalization to other planetary missions and future datasets.
